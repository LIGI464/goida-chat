# Parallel feature smoke matrix

Независимая ручная QA-проверка функций из `origin/feat/invite-links`. Матрица не изменяет product code: сценарии запускаются против локального Docker-стенда или тестового deployment, а результаты и evidence записываются в этот файл или в копию для конкретного прогона.

## Быстрый запуск

1. Создайте тестовые аккаунты: владелец group chat, обычный участник и отдельный пользователь для invite. Для гостевого сценария используйте чистое private/incognito окно.
2. Поднимите зависимости и приложение по инструкции в [`README.md`](../README.md) или подключитесь к тестовому URL. Убедитесь, что API `/health`, Socket.IO и LiveKit доступны.
3. Проверьте каталог сценариев и получите run sheet:

   ```bash
   npm run qa:smoke-matrix
   npm run --silent qa:smoke-matrix:markdown > parallel-feature-smoke-run.md
   ```

   В PowerShell используйте `npm run --silent qa:smoke-matrix:markdown | Out-File -Encoding utf8 parallel-feature-smoke-run.md`. Флаг `--silent` исключает служебные строки npm. Храните заполненный отчёт отдельно от шаблона и не добавляйте тестовые файлы в Git.

4. Откройте run sheet, заполните фактический результат, найденные ошибки и severity. Для каждого дефекта приложите timestamp, URL/commit приложения, account role, console/network log и короткую запись экрана или screenshot.
5. Выполняйте voice-сценарии на физических наушниках и с разрешёнными microphone/camera. Для сетевых проверок используйте DevTools Network throttling/Offline. Для размера файлов проверяйте байтовый размер, а не округлённые мегабайты: лимит — 104857600 bytes (100 MiB), если deployment не задаёт иной контракт.

Команда без флага печатает количество сценариев и проверяет, что у каждого есть ID, шаги, ожидаемый результат и поля для evidence. Флаги `--markdown` и `--json` предназначены для формирования листа прогона и интеграции с внешним test-runner.

## Критерии результата

- **Pass** — ожидаемый результат подтверждён, в консоли и network нет необъяснимых ошибок.
- **Fail** — поведение отличается от ожидаемого или функция ломает соседний сценарий; заведите дефект и укажите severity.
- **Blocked** — невозможно проверить из-за окружения/прав доступа; приложите причину и prerequisite.

Severity: `S0` — потеря доступа/данных или полная недоступность; `S1` — критическая функция не работает или есть утечка доступа; `S2` — существенная деградация с обходным путём; `S3` — косметика, текст или редкий edge case.

## Условия воспроизводимости

Матрица описывает целевой набор функций параллельных веток. Базовый commit `bc344ae` сам по себе не включает весь этот набор. Отсутствующий UI/API фиксируйте как `Blocked` с указанием отсутствующей функции; не заменяйте гостевой вход регистрацией и не считайте fallback подтверждением работы RNNoise/Speex. Для каждого браузера и каждого аудиорежима создавайте отдельную строку результата с точной версией браузера. CLI проверяет структуру каталога, но не выполняет браузерные сценарии.

Для AUDIO-01 один цикл — включение выбранного процессора, ожидание готовности, проверка звука вторым участником и выключение. Выполните 50 циклов RNNoise и 50 Speex, если оба доступны. Запишите CPU, память, число активных tracks/AudioContext до старта и после циклов 10, 25, 50; после выхода из комнаты проверьте освобождение микрофона. Повторите несколько быстрых переключений и выход из room во время инициализации. Рост памяти сам по себе — наблюдение; дефект утечки требует повторяемого роста удерживаемых ресурсов после очистки.

Для AUDIO-02 запишите requested/effective mode, fallback reason, capture settings и ошибки загрузки WASM/worklet. Сравните raw/browser/RNNoise/Speex на одинаковом речевом и шумовом фрагменте. Отключённый или недоступный режим отмечайте отдельно, а не общим Pass для четырёх режимов.

Для файлов используйте границу 100 MiB = 104857600 bytes; дополнительно проверьте десятичные 100 MB = 100000000 bytes, если UI пишет «МБ». Для создания файлов в отдельном временном каталоге (PowerShell):

```powershell
$qaFiles = Join-Path ([System.IO.Path]::GetTempPath()) ('goida-qa-' + [guid]::NewGuid())
New-Item -ItemType Directory -Path $qaFiles
foreach ($size in @(100000000, 104857600, 104857601)) {
  $file = Join-Path $qaFiles ("boundary-$size.bin")
  $stream = [System.IO.File]::Open($file, [System.IO.FileMode]::CreateNew)
  try { $stream.SetLength($size) } finally { $stream.Dispose() }
}
Get-ChildItem -LiteralPath $qaFiles | Select-Object Name, Length
Get-ChildItem -LiteralPath $qaFiles | Get-FileHash -Algorithm SHA256
```

Сравните SHA256 исходного и скачанного файлов. В FILE-02 отдельно проверьте серверный отказ: UI может остановить oversized файл до сетевого запроса. Повторите upload напрямую по API-контракту проверяемого deployment с валидной тестовой сессией и зафиксируйте статус ответа и отсутствие сохранённого объекта.

Для INVITE-01 используйте независимые токены для revoke и expire и пользователей, которые ещё не состоят в комнате: существующий membership не доказывает обход проверки токена. Запишите отдельные результаты create/join/revoke/expire. Если нет настройки TTL, подготовьте fixture на изолированной тестовой БД; зафиксируйте token ID, expiresAt и серверное время без публикации самого токена.

Для FILE-03 аналогично подготовьте отдельный attachment с коротким сроком действия в тестовой среде. Проверьте новый запрос preview/download и ранее сохранённый URL после expiresAt, в том числе до запуска фоновой очистки. Не меняйте системное время рабочей машины или production-данные ради expiry-теста. Если fixture/TTL недоступны, результат — Blocked с причиной.

Для NETWORK-01 подтвердите фактический обрыв Socket.IO и LiveKit: режим Offline в DevTools может не закрыть уже открытые соединения. При необходимости отключите сеть на тестовом устройстве; зафиксируйте время восстановления, отсутствие дублей и очистку устаревшего presence. Проверку реального iOS указывайте отдельно от эмуляции desktop-браузера.

## Evidence и отчётность

Для каждого Fail/Blocked добавьте запись в issue с ID сценария и приложите:

- время прогона и timezone;
- браузер и версию, ОС и viewport;
- commit/deployment URL и роли тестовых аккаунтов (без секретов);
- шаги воспроизведения, ожидаемое и фактическое поведение;
- severity по шкале выше;
- screenshot/видеозапись, console log и относящийся network request.

После прогона сохраните заполненный run sheet рядом с отчётом релиза. Незаполненное поле «Фактический результат» означает, что сценарий не проверен, а не что он прошёл.
